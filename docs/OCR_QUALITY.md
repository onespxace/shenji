# OCR 准确率实测与改进记录

> 版本：2.2 · 初测：2026-09-26 · 结构化识别引擎：2026-09-26
> 起因：用户反馈"识别凭证准确率不高"。本文记录**实测数据**与据此做出的改动，
> 避免后续出现"文档说提升了、实际没提升"的情况。

> **⚠ 结论已更新**：本文第 2~3 节记录的是"在 Tesseract 内部调优"的结论，
> 那些结论本身没有错，但**天花板确实很低**。第 8 节起是第二阶段：
> 引入 PaddleOCR PP-OCRv5 + 结构化字段识别，把字段命中率从 65.0% 提到 97.5%。
> **只读第 2 节会得出错误结论，请连着第 8 节一起看。**

## 1. 怎么测的

不看宣传数字，直接建一套带标准答案的测试集，逐字段对分。

| 编号 | 图片 | 模拟场景 | 生成参数 |
|---|---|---|---|
| A | `A-scan.png` | 扫描件 | 纯黑字、无旋转、无噪点、JPEG 100 |
| B | `B-skew.png` | 轻微倾斜 | 灰度 25、旋转 −2.2°、JPEG 80 |
| C | `C-lowcontrast.png` | 低对比度 | 灰度 118、噪点 14、JPEG 88 |
| D | `D-photo.png` | 手机翻拍 | 灰度 168、旋转 −1.4°、噪点 26、JPEG 58、字号 15 |

每张图 10 个必答字段（日期、凭证号、摘要、金额、附件张数、2 个科目、3 个签名），
共 40 个字段。归一化时容忍 OCR 常见的空格、全角、`O/0`、`l/1` 混淆。

```bash
cd web
node scripts/bench-ocr.mjs --make-images   # 生成测试图 + 标准答案
node scripts/run-ocr-bench.mjs             # 模型 / 版面模式横向对比
node scripts/prep-bench.mjs --prep         # 生成 5 种前处理变体
node scripts/cmp-prep.mjs                  # 前处理变体对比
node scripts/cmp-twopass.mjs               # 分区二次识别验证
```

测试图与备选模型共约 34 MB，落在 `web/.bench-ocr/`（已 gitignore），不入库。

## 2. 实测结果

### 2.1 换模型、换版面模式：没有收益

| 配置 | A | B | C | D | 平均 |
|---|---|---|---|---|---|
| **tessdata_fast · AUTO（现状）** | 9/10 | 9/10 | 9/10 | 5/10 | **80.0%** |
| best_int · AUTO | 9/10 | 9/10 | 9/10 | 5/10 | 80.0% |
| best_int · 单一区块（PSM 6） | 5/10 | 5/10 | 5/10 | 5/10 | 50.0% |
| best_int · 单列（PSM 4） | 9/10 | 9/10 | 9/10 | 5/10 | 80.0% |
| best_int · 仅中文 · 单一区块 | 5/10 | 5/10 | 5/10 | 5/10 | 50.0% |

结论：

- `4.0.0_best_int` 模型与 `tessdata_fast` **实测完全持平**。不换——换上去要多背
  4.5 MB 体积却换不到一个百分点的准确率。
- **PSM 6（单一区块）比自动版面差 30 个百分点**。凭证是带列线的表格，
  强制当成一整块会把列打散。保持 `PSM.AUTO`。
- 真正的瓶颈是 Tesseract 的中文 LSTM 模型，不是图片质量。

### 2.2 图像前处理：越处理越差

| 变体 | A | B | C | D | 总分 |
|---|---|---|---|---|---|
| **原图（不做前处理）** | 9/10 | 9/10 | 9/10 | 5/10 | **80.0%** |
| 1x（等比复制对照） | 9/10 | 9/10 | 9/10 | 5/10 | 80.0% |
| 2x 放大 | 9/10 | 8/10 | 7/10 | 5/10 | 72.5% |
| 2x + 灰度 | 9/10 | 8/10 | 7/10 | 5/10 | 72.5% |
| 2x + 灰度 + 对比度拉伸 | 9/10 | 4/10 | 7/10 | 5/10 | 62.5% |
| 再加二值化（阈值 160） | 5/10 | 6/10 | 5/10 | 5/10 | 52.5% |

这是最反直觉的一条：**手工前处理把准确率从 80% 打到 52%**。原因有二：

1. Tesseract 内部已经做了 Otsu 二值化，先做一遍等于用更差的结果覆盖它。
2. 固定阈值 160 会抹掉笔画抗锯齿、把表格线加粗，干扰版面分析。

**因此本项目不引入任何图像前处理。** 曾写过的 `prep-bench.mjs` 保留为反例证据。

### 2.3 分区二次识别：零收益

对签名带（底部 22%，3 倍放大，仅中文模型单行模式）和金额区（右侧 40%，
3 倍放大，英文模型 + 数字白名单）分别二次识别再与首遍合并：

```
首遍合计    32/40  80.0%
二次识别后  32/40  80.0%
```

**一个字段都没救回来。** 原因是失败模式不是"认错"而是"根本没认出来"——
翻拍图里表格正文整块丢失（`收到股东投资款`、`银行存款`、`实收资本` 全部消失），
没有可以被纠正的候选文本。签名的 `王五` 被读成 `EA` 属于认错，
但 2 个中文字的姓名没有可对照的候选集合，猜不回来。

## 3. 真正有效的那一条

死磕"提高平均准确率"这条路，实测已经走到头。但实测里有一个信号非常有用：

```
词级数量: 70     整页置信度: 90
低置信(<80) 词: 凭证(12) ？(73) ？(73) ？(67) EA(56)
签名行附近:   审核(92)  EA(56)
```

**整页置信度 90，但被认错的 `王五`→`EA` 只有 56。**
错字的词级置信度显著低于整页均值——也就是说，**错的位置是可以精确定位的**。

问题从"平均准确率 80% 够不够"变成了"**我该去哪里核对**"。这才是用户真正需要的。

### 3.1 拍摄质量闸门（识别前）

新增 `web/src/lib/ocr-quality.js`，在跑 OCR 之前先算：

- 清晰度（拉普拉斯响应方差）
- 对比度（灰度标准差）
- 亮度均值（过暗 / 过曝）
- 倾斜角（投影剖面，±6° 内搜索）

输出 `good` / `warn` / `poor` + 分数 + 具体原因 + 可执行建议。

真机验证（翻拍图 D）：

```
画质不足，建议重拍（18 分）
清晰度 38 · 对比度 16 · 亮度 244 · 倾斜 1.5°
- 画面偏模糊（清晰度 38，建议 ≥ 42）
- 对比度不足（16，建议 ≥ 26）
- 整体过曝发白
识别完成，但这张图画质不足（18 分），错误率会明显偏高，请优先重拍
```

### 3.2 逐字段置信度（识别后）

`voucher-validator.js` 接收词级置信度，按字段回查：

- 取该字段匹配到的词的**最低**置信度（不是平均——见下）
- 低于阈值（默认 78）的字段：检查项由 `pass` **降级为 `warn`**，并在详情里写明置信度
- 关键字段（日期、凭证号、借贷金额、平衡、科目、签名）置信度不足时，
  **不允许给出"形式要素基本完整"**，最高只能到"需要人工复核"

**为什么取最低而不是平均。** 签名字段由多个词组成，实测值是 90 / 90 / 56。
取平均是 78.67 → 四舍五入 79，刚好越过阈值 78，**唯一的错字被平均抹掉了**，
用户看不到该核对哪里。取最低就是 56，立刻暴露。

**为什么日期要用原始匹配文本。** 日期被规范化成 `2024-05-03`，
而 OCR 原样是 `2024年5月3日`，规范化之后再也匹配不到词级置信度。必须用 `raw`。

### 3.3 效果对比

同一张扫描件（A-scan），改进前后：

| | 改进前 | 改进后 |
|---|---|---|
| 整体结论 | 形式要素基本完整 ❌ | **需要人工复核** ✓ |
| 提示 | 无 | 会计科目(67%)、责任签名(56%) |
| 签名错误是否可见 | 否 | 是，明确指向 56% 的那一项 |

翻拍图（D-photo）：整体结论 `存在缺失或不平衡`，列出 5 个待核对字段
（凭证日期 67%、经济业务摘要 0%、借方金额 71%、贷方金额 71%、借贷平衡 71%）。

**这就是本次改动的实际价值：不是把 80% 变成 90%，而是让错的位置再也藏不住。**

## 4. 明确的局限（不夸大）

- 上面的准确率是**合成测试图**的数字：字是渲染出来的，不是手写。
  真实凭证有手写金额、签字、印章遮挡、复写纸洇色，**只会更差，不会更好**。
- 手写签名与手写金额不在本工具的能力范围内。签名项只是"标签后面有没有文字"，
  判断不了笔迹真伪。
- `80%` 是**字段命中率**，不是"凭证正确率"。工具不判断经济业务是否真实、
  是否重复报销、是否有舞弊，这 7 项固定列在界面的"本工具不判断"里。
- 倾斜角估计的符号与拍摄方向相反（页面顺时针旋转被判为负值），
  界面只取绝对值，不影响判定。

## 6. 如果以后还想提高准确率

按实测收益排序，**都已验证无效，不要重复试**：

1. ~~换 best_int 模型~~ — 持平
2. ~~灰度 / 拉伸 / 二值化 / 放大~~ — 更差
3. ~~改 PSM~~ — AUTO 最优，PSM 6 差 30 个点
4. ~~分区二次识别~~ — 零收益

还有价值的路（当前未做）：

- **换成支持手写的中英混合引擎**（如 PaddleOCR / 云端 OCR）。这需要引入
  新的运行时与模型体积，且与"本地优先、不上传原始文件"的约束冲突，
  要先确认取向。
- **引导用户拍摄**（用质量闸门的检测结果做实时提示，拍不好当场就重拍，
  而不是识别完才发现）。当前质量闸门只在识别时触发。
- **把质量闸门的检测前移到选图瞬间**，拍完立刻给分。

# 8. 第二阶段：凭证结构化识别引擎（PaddleOCR PP-OCRv5）

第 2~3 节的结论只覆盖"Tesseract 内部调优"这条路的天花板。真正的瓶颈不是参数，
而是**"整页 OCR 拼成一段文本，再靠正则猜哪段是摘要、哪段是金额"这个范式本身**。
本阶段把范式换掉。

## 8.1 为什么换引擎

第 2.2 节已经证明：Tesseract 在翻拍图上会**丢失整块表格正文**，
而且靠调 PSM、改模型、加前处理都救不回来——因为失败模式是"没产生候选文本"，
不是"认错了字"。

PP-OCRv5 用的是**检测式**识别（DB 文本检测 + 识别模型），先找文字框再逐框识别，
输出天然带坐标。这正好对上凭证这种"版式固定 + 带框线表格"的结构。

## 8.2 结果

| 方案 | 字段命中 | 平均耗时 |
| --- | --- | --- |
| 基线：Tesseract 整页 OCR + 正则解析（原实现） | 65.0%（26/40） | 479 ms |
| 新管线：PP-OCRv5 + 结构化解析 | **97.5%（39/40）** | 2780 ms |
| 差值 | **+32.5 个百分点** | 5.8× |

分退化条件：扫描件 70→100，轻微倾斜 70→100，低对比度 70→90，**手机翻拍 50→100**。

完整数据、评分口径与两次口径修正记录见
[`web/src/ocr/benchmark/records/benchmark-20260926.md`](../web/src/ocr/benchmark/records/benchmark-20260926.md)。

**诚实说明的三点**：

1. 测试集是**合成渲染图**，不是真实凭证。真实凭证叠加手写、印章遮挡、复写纸洇色，
   表现只会更差。界面与文档只写"当前测试集字段识别结果"。
2. 有一个**真实回归**：借方金额 4/4 → 3/4（低对比度图列边界误判），尚未修复。
3. 耗时 5.8 倍是实打实的代价，靠按需懒加载 + 定向重识别缓解，没有消除。

## 8.3 架构

```
src/ocr/
├── engines/
│   ├── engine-registry.js     引擎统一契约 + 几何工具
│   ├── paddle-engine.js       PP-OCRv5（动态 import，不进主包）
│   └── tesseract-engine.js    保留为 fallback + benchmark 基线
├── pipeline/
│   ├── field-extractor.js     行聚类 → 表头锚点 → 列角色 → 字段
│   └── credential-pipeline.js 主编排 + 定向重识别
├── validators/
│   ├── field-validators.js    日期/编号/金额/科目字典
│   └── signature.js           签名只判存在性
├── confidence/reliability.js  字段级可靠度
└── benchmark/                 测试集、评分口径、实测记录
```

**契约**：引擎只负责"图 → 带坐标的文本行"，**不做任何字段解析**。
字段解析统一在 `field-extractor.js`，避免又滑回"猜列"的老路。

## 8.4 关键设计决策

### 先定位结构，再识别文字

列归属按**文本框左边缘**落在 `[列左边界, 下一列左边界)` 判定，
列右边界取"与下一表头左边缘之间"。

踩过的坑：最初用"中心点落在表头宽度内"判定，而「摘要」表头只有 2 个字宽、
`收到股东投资款` 有 7 个字宽，导致**摘要列在 4 张图上全部抽取失败**。
改用左边缘 + 下一表头边界后修复。

### 形近科目必须封顶，不靠调参

科目字典匹配：完全相同才自动采纳；编辑距离 ≤1 且长度 ≥3 只作候选列出，
**绝不改写识别值**。界面上显示"识别结果"与"规范化匹配"两行，由用户决定。

但光把 dictionary 权重设成 0.15 是不够的——实测 `ocr=0.9、format=1、context=1` 时
加权平均仍能到 **0.90**，高于 0.85 的"可靠"阈值，于是**没被证实的科目被标成可靠**。
所以加了硬封顶：`matchType` 为 fuzzy/none 时，可靠度一律压在阈值之下。
这是"禁止无证据幻觉"必须有的硬约束，不能靠调参碰运气。

### "不适用"与"未知"必须分开

- **未知**（有这项检查但没结论）→ 按 0.5 计入并扣分
- **不适用**（这类字段根本没有该约束，如制单人的上下文一致性）→ 不进加权

一开始没分清，导致"缺 OCR 置信度"时该子分被整个剔除，
**字段得分反而变高**（0.95 → 可靠）。方向完全反了，已修：缺证据一律按未知扣分。

### 定向二次识别只跑 ROI

只对"分数低 / 格式非法 / 空"的字段跑第二次，**绝不整页重跑**。
多次结果不一致时标记 `uncertain`，不做"多数投票后就一定正确"。

### 签名重新定义为"存在性检测"

依据：PP-OCRv5 官方公开评测对手写中文识别准确率约 **41.7%**，
签名这件事本身在能力边界之外。输出只有三种状态：

| 状态 | 含义 |
| --- | --- |
| `present` | 存在签名区域且有文字 |
| `absent` | 识别到签名栏但后面没文字（疑似空签） |
| `uncertain` | 连签名栏都没识别到，或 OCR 结果不像中文人名 |

界面固定显示："签名仅做是否存在/是否异常检测。OCR 读出的文字不构成身份证明，
也不能替代手写笔迹鉴定。"

**永不出现** `签名：王五（确认）` 这种表述。

## 8.5 隐私与部署

- PP-OCRv5 模型（20.55 MB）**自托管**在 `public/ocr/paddle/`，由
  `npm run sync:paddle` 拉取，不入库、不走第三方模型 CDN
- 用户凭证图片**不上传**。只有 ONNX Runtime 的 wasm 走 jsDelivr（只下载运行时）
- 引擎走 `import()` 动态加载，22 MB 运行时拆成独立 chunk，
  **只有点击"逐字段识别"才拉取**；主包只增加约 80 KB
- OCR 全部在浏览器本地完成，GitHub Pages 纯静态部署不变
